## Reproduced material findings

### R1 — P1: protect cached priority records before exposing them

Locations: [`src/proxy/sessionStore.ts:740`](https://github.com/rynfar/meridian/blob/6558c209f8bddf8e59b554d16c9834381c7817c2/src/proxy/sessionStore.ts#L740), `:961–969`, and `:1223–1235`.

`loadMeta()` constructs mutable priority records. `committedDocument()` installs mutable metadata after a write. `lookupPriorityAssignmentResult()` returns the cached assignment and attempt by reference; unlike ordinary session lookups, it does not freeze them. A same-sequence `freshStoreCache()` reuses those objects, and the next mutation compares/drafts against the already altered authority. The former JSON implementation deeply froze metadata when caching it.

The exact-head probe publishes a route with profile `work`, changes the returned assignment to `mutated-in-memory`, and observes that value on a second lookup while SQL still contains `work`. More materially, it durably blocks a trusted turn at issue time 200, proves that an older turn at 100 is rejected, changes the returned cached `blockedTurnIssuedAt` to 0, and submits the same older turn again. It now wins even though the persisted blocked floor was still 200 before the claim. These are supported exported store operations over valid synthetic records, not direct edits to the SQL authority.

The identical probe on `c159bf9` reports frozen assignment/attempt objects, rejected mutations, and rejection of the older turn. This is a regression introduced by SQL caching. Correct it by retaining immutable authority (or returning detached immutable views) for every priority assignment, attempt, and rollback mapping while keeping internal slot mutation private. Add direct tests for both fresh-load and post-commit caches, including an attempted blocked-floor mutation followed by a fenced claim. No new public API approval is needed to preserve the existing protection.

Evidence: `probe-sql.stdout.json`, case `immutable-priority-authority` (`FAIL`); `probe-async-json.stdout.json`, same case (`PASS`).

### R2 — P1: serialize digest verification and legacy file retirement with old writers

Locations: [`src/proxy/session/storeDatabase.ts:465–484`](https://github.com/rynfar/meridian/blob/6558c209f8bddf8e59b554d16c9834381c7817c2/src/proxy/session/storeDatabase.ts#L465), and `src/proxy/sessionStore.ts:1099–1169`.

`retireImportedFile()` awaits a read, verifies its digest, then separately awaits the rename. Mapping migration holds a database transaction/queue, not the legacy `sessions.json.lock`; an older JSON writer does not participate in the SQL lock. The path can therefore change after verification and before retirement. The comment promising that a rewritten file remains for the next start is false in that interleaving.

The deterministic probe provides digest A, then injects a valid old-writer publication between verification and actual rename: take the legacy lock, fsync replacement B, rename B over the canonical path, release the legacy lock. Retirement archives B under `.migrated-*`, removes the canonical file, and returns success even though only A was declared imported. Its archived digest differs from A. B's bytes remain physically in the archive, but they are absent from active SQL authority and startup does not import those archives. This hides a successfully published old-writer update rather than preserving it for the next start.

Correct it with one documented migration/writer protocol. If concurrent old writers remain supported, take the exact legacy writer lock across snapshot/import/verified retirement and define how later publications are admitted; a second digest check followed by another unlocked rename still races. If the chosen contract requires writers stopped, enforce a barrier and fail closed rather than describing an unsupported merge as safe. Preserve a deterministic writer-versus-retirement test and interrupted-import restart coverage. Lifecycle migration already holds its legacy lifecycle lock, so the reproduced unlocked-retirement defect is specifically the mapping path.

Evidence: `probe-sql.stdout.json`, case `retirement-digest-rename-race` (`FAIL`, one intercepted rename, canonical file absent, `unimportedUpdateArchived=true`). The probe tests the exact retirement helper with a synthetic writer publication; it does not run an installed old Meridian process.

### R3 — P1: legacy lifecycle rows cannot overwrite live leases and newer fences

Locations: [`src/proxy/sessionLifecycle.ts:1892–1896`](https://github.com/rynfar/meridian/blob/6558c209f8bddf8e59b554d16c9834381c7817c2/src/proxy/sessionLifecycle.ts#L1892), `:1917–1921`, and the merge test at `src/__tests__/session-lifecycle.test.ts:1160–1187`.

`mergeLegacySidecar()` unconditionally replaces a stored record with the JSON record for the same transcript. Taking the maximum of fence counters does not preserve active publication/executor/deletion owners, the newer resource generation, or a deletion tombstone. Keeping the lifecycle file lock serializes the import but does not make a stale record authoritative.

The exact-head probe prepares a publication target owned by the still-running process and observes one durable publication lease. A GC positive control removes nothing. A valid legacy journal then represents the same physical target as retired and omits its active leases; this is the kind of independent record an old process can write after it starts with an empty retired JSON path. An unrelated ordinary lifecycle registration triggers the actual legacy import. The publication lease count drops from 1 to 0 and the resource becomes retired. The ordinary `runGc()` path, using its supported synthetic `deleter` option, deletes the protected target and marks it deleted while its publication owner is alive.

The probe does not delete an SDK transcript or consume a model call; it records the exact GC deletion decision with a stub. The total synthetic deletion count is 2 (an unrelated unpinned fixture is also collected); **targetDeletions=1** proves the specific protected resource was selected. The initial aggregate-only record is retained separately to avoid presenting the count as two protected deletions.

The new legacy merge test explicitly expects JSON to replace the SQL record, but its target has no concurrent publication/deletion/executor authority. It misses this destructive case. Define a conflict merge that preserves newer generation/tombstone and live fenced ownership, or prohibit competing old writers with an enforced migration barrier. Add real-process merge races around publication, active executors, deletion claims, restored publication leases, and deleted tombstones. If ownership cannot be safely reconciled, reject the merge before making a target collectible.

Evidence: `probe-sql.stdout.json`, case `legacy-journal-preserves-publication-owner` (`FAIL`, publication lease 1→0, target deleted); positive control assertions are in `sqlite-safety-probes.mjs`.

### R4 — P2: the retained pending-eviction test no longer creates a pending SQL write

Locations: [`src/__tests__/proxy-request-cancellation.test.ts:270–283`](https://github.com/rynfar/meridian/blob/6558c209f8bddf8e59b554d16c9834381c7817c2/src/__tests__/proxy-request-cancellation.test.ts#L270) and `:322–339`.

The retained arrival-snapshot test calls `holdStoreFileSync()`, whose hook recognizes JSON headers in Node `FileHandle.writeFile()` and delays their `sync()`. Native SQL writes never take that path. The test releases after 100 ms without proving that the hook was entered or the eviction remained pending. It can pass without exercising the request-versus-owned-eviction ordering it claims to retain.

Instrumenting the exact hook mechanism shows SQL `gateEntries=0` and eviction already settled before release; the same async JSON baseline shows `gateEntries=1` and an unsettled eviction. This is a test-coverage defect, not proof that request ordering itself is currently broken. Replace it with an SQL transaction gate that asserts entry, blocks the actual eviction used by this path, asserts the arrival snapshot cannot pass it, then checks the resulting generation. The existing `holdStoreWrites()` helper wraps `.transact()`; the mapping path uses `.transactNow()` inside its queue, so blindly swapping helpers is insufficient.

Evidence: both probe JSON files, case `retained-arrival-eviction-hold`.

## Remaining semantics and evidence

- **Durability and exclusion:** small row deltas, `BEGIN IMMEDIATE`, serialized local queue, writer `synchronous=FULL`, and post-COMMIT cache updates are sensible. SQL lock release on process exit removes JSON stale-store-lock recovery needs; retaining the lifecycle file lock preserves its admission/deadline/owner protocol. Existing CAS contention and killed-before-import tests are useful and should remain. They do not cover R1–R3.
- **Event loop:** the installed promise wrapper's native asynchronous `.exec()` does offload BEGIN/COMMIT waits. Prepared writer statements are retained to avoid a finalizer acquiring a connection mutex held by those waits. However, `.run()` remains synchronous, and first-open reader WAL/schema setup is synchronous with a potentially 10-second busy timeout (`storeDatabase.ts:191–220`). The broad “reader never waits” and “event loop stays free” claims need qualification; SQLite documents BUSY during recovery, last-connection cleanup, and exclusive access. Validate cold concurrent startup/schema creation, crash recovery, page-cache spill/checkpoint pressure, and supported Node/platform packaged execution, with heartbeat and measured p95/p99. [SQLite BUSY discussion](https://www.sqlite.org/wal.html#sometimes_queries_return_sqlite_busy_in_wal_mode).
- **Publication integrity:** putting lifecycle and mappings in one DB does not combine their existing multi-stage publication into one SQL COMMIT. Correctly preserving leases remains essential. Verify crash boundaries and uncertain COMMIT after durable publication, including another writer committing before `landedDespiteError()` observes the single last-commit token. This review did not reproduce that latter race, so it is an evidence requirement, not a fourth application defect. Do not replay an operation whose publication outcome is unknown.
- **Incremental caches:** sequence/changed-row tracking reduces reparsing, and lifecycle counter regression forces revalidation. Keep malformed row/counter tests. The cache assumes all database writers follow the sequence protocol; define supported diagnostics/repair behavior and reject unsupported schema versions before mutating authority. Direct SQL repair must not silently bypass sequence or fences. No user SQL editor/API is proposed or approved.
- **Corruption and failures:** tolerant mapping lookups versus strict reads/mutations are retained, and malformed legacy JSON is left in place. Required future evidence includes malformed/current/newer schema and rows, truncated DB/WAL, permission/disk-full/commit failures, failed rollback, file replacement during connection reuse, and restart. Store opening performs schema setup before all format checks; fail-closed behavior must be proven against unsupported authority. An OFF-synchronous schema reader must never be allowed to perform an unsynced checkpoint; source intentionally disables its auto-checkpoint and closes it before the FULL writer.
- **Packaging/platform:** `libsql` is an existing dependency, so this contribution adds no package in the diff. It newly makes the native database and `libsql/promise` path mandatory for sessions. `scripts/build.ts:15` does not externalize libsql; only SDK/jsonc-parser are listed. Contributor's bundled Node 26 experiment is not an installed, relocated Node 22 package check. Validate the actual supported Node 22 CLI/server exports, relocated installed native module, migration, multi-process ownership, restart and rollback on Linux GNU/musl, macOS, and Windows as applicable. Current Windows CI includes durable/GC smoke subsets, not full SQL migration/CAS/priority/corruption tests. The new release helper improves native handle cleanup in those subsets; other fixtures still remove directories while cached DB connections may exist, which is an unproven Windows/full-suite compatibility concern.
- **Retained tests and CI:** `package.json:28` excludes `**/*session-store*` from the main stage and never adds `priority-session-store.test.ts` back. This PR changes 29 hunks in that file and its author separately ran it, but the required test job does not execute it. Wire the direct priority store suite into its isolated required stage. Adapted tests should assert their injected failure/hold was reached; a green output from an unused FileHandle hook is insufficient.
- **Live proof:** the PR body admits its four real-Claude E2E scripts were syntax-checked and not run. Its production-day and overloaded-host metrics are contributor reports, with raw reproducible evidence absent, and the performance baseline predates main's #1204. Local API fixtures/mocked SDK and the synthetic probes here cannot establish actual resumed-turn, publication, cancellation, profile-copy prune, concurrent GC, or stalled-disk behavior through the affected real model/client/platform. Use the implicated client path (including the Meridian OpenCode plugin where OpenCode is implicated), exact model/SDK/platform, and preserve before/after headless scripts/results durably. No live credentials were sought or used by this reviewer.
- **Engineering boundaries:** the new `session/storeDatabase.ts` keeps native persistence below orchestration and introduces no detected dependency cycle into pure lineage or leaf modules. The one orchestration change updates await behavior inherited from async cleanup. Removing `directoryEntryExists()`/JSON durability tests is reasonable only where the SQL authority truly replaces them; retain directory sync behavior for migrated archives and lifecycle locks.
