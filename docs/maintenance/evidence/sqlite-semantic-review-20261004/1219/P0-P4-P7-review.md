## Findings and required corrections

1. **Shutdown ownership and completion** (`src/proxy/server.ts:10035-10062`). After forced HTTP closure, the cached close promise waits at most 2 seconds for request cleanup. With cleanup still active it correctly withholds GC/backend release, but fulfills `Promise<void>` nevertheless. No later request finalizer schedules handle release, and another close returns the already-fulfilled promise. Thus an embedding caller can observe completion while SQL ownership remains, without an eventual joined release. The corrected [actual-close probe](P4-shutdown-probe/result.json) reproduced this on macOS arm64/Bun 1.3.14: close fulfilled at 2519 ms while the finalizer was deliberately paused, then the unchanged real SQL lease release completed. At 250 ms and 1000 ms after finalizer completion and a repeated cached close, the native connection, backend and exclusive-maintenance refusal remained. OS ownership became available only after the probe process exited. The first run failed a /tmp versus /private/tmp fixture comparison; its complete history and the one-line realpath correction are retained. SDK/auth boundaries were mocked: one mock query, zero real inference, credential reads or SDK children. This observation is not Linux/client/model E2E. Keep guard ownership until joined; specify truthful bounded failure/eventual release under owner-approved public close semantics. Preserve a negative control against early release.

2. **Already-approved cleanup contract is not implemented by SQL** (`src/proxy/session/cache.ts:137-153`, `bookkeeping/runtime.ts:90-95`). Source clearSessionCache still returns void; SQL clears durable state before memory and silently returns on failure, retaining memory. JSON clears memory first. #1244 already approved immediate in-memory reset, ordered asynchronous durable completion via Promise<void> and existing best-effort cleanup error policy. Reuse that approval; do not request it again. SQL synchronous writers outside admission can be busy, so address the actual failure and waiting paths.

3. **Public/operator contract remains unapproved** (`server.ts:223`, `:9717-9722`, `:9832-9842`; `bookkeeping/runtime.ts:35-80`; configuration guide's admission/embedding section). New exported initializeProxyBookkeeping returns a handle exposing path, reader and close; start waits for initialization, create requires prior initialized ownership, and Claude now has closeBackend. The exact exposed surface, lifecycle failure/idempotency/multi-instance/directory semantics and trustworthy close completion need a tracked owner decision. No ProxyConfig field or header/profile/health response-shape change was identified in the SQLite packet.

4. **Proof boundary for packaging**. The libsql relocation script independently installs a tarball, imports the public server, resolves native libsql from the install, persists/reopens telemetry and checks loader/build-path leakage; it establishes native loading only when actually run on the final artifacts/platform. The bookkeeping smoke independently installs explicit candidate and baseline, uses real two-process HTTP ownership/migration/restart/export controls, and clearly claims no live SDK turns. It does not publish or mutate native model history. The GC packaged smoke borrows checkout node_modules, seeds/reads JSON, scans markers and invokes a fenced SDK deletion child: it is not independently installed SQL-GC or live affected-client evidence. Preserve that distinction. Final installed package, Linux/native Windows, GC under load, actual affected-client/model/SDK/platform and restart/rollback/publication gates remain open.
