## Material findings

### F1 (P2) — GC claim holds one synchronous writer transaction across every deferred/pinned page

Evidence status: reproduced. Locations: `src/proxy/session/bookkeeping/lifecycleDeletionSql.ts:45-67`; `src/proxy/session/bookkeeping/resources.ts:144-154`; `src/proxy/session/bookkeeping/resourceImport.ts:17-25`; `src/proxy/session/bookkeeping/migrationImport.ts:51-56,74-80`; `src/proxy/session/bookkeeping/transaction.ts:298`.

LIMIT 128 bounds each retired SELECT, but while(true) stays inside one BEGIN IMMEDIATE callback until an eligible row or complete exhaustion. Every skipped row is hydrated. run deadline checked only before claim; admission cancellation does not interrupt started transaction. Offline import preserves arbitrary resource counts independently of runtime caps.

A valid deferred/imported or durable-pinned ledger blocks the event loop and all competing SQL writers despite maxDeletesPerRun=1/runTimeoutMs=5. Actual 25ms writer rejected on 4096/16384-row arms; one-row negative controls committed. No default-budget failure or Linux/Windows timing was measured.

Required correction: Bound rows/work per claim transaction and yield/release between batches. Preserve exact pin/lease/claim predicates, re-read authority at destructive claim, and use explicit progress state so repeated sweeps do not permanently rescan only oldest blocked entries. Preserve intended candidate ordering or document/approve any changed ordering. Add future-backoff, NULL/exact durable pin, all-leased, late eligible and concurrent-writer controls.

### F2 (P2) — GC deferred accounting hydrates the whole backlog in one synchronous read snapshot after the claim budget

Evidence status: causal source path plus isolated phase measurement. Locations: `src/proxy/session/bookkeeping/lifecycleDeletionSql.ts:153-157`.

SELECT all retired/deleting keys followed by readResource and pin lookup for each row; no paging/yield/deadline applies. Even zero-deferred all-pinned rows take this path.

Measured phase/timer delay 263.2ms for 4096 all-pinned rows with deferred=0; 625.9ms for 16384 future rows. Claim-only lock timing is separately recorded; total minus claim is not claimed as an exact isolated count-only duration.

Required correction: Avoid full JS resource hydration for count/accounting and establish a bounded responsiveness strategy while preserving deferred/pin semantics. An aggregate/filter SQL projection may reduce hydration, but do not claim a wall-time bound merely from a single SQL statement. Add an explicit large zero-deferred pinned control and event-loop responsiveness control.

### F3 (P2) — SQL cache clear retains memory caches on durable clear failure and conflicts with approved #1244 reset policy

Evidence status: confirmed static regression; cross-packet P4 caller, previously recorded bounded review finding. Locations: `src/proxy/session/cache.ts:134-152`; `src/proxy/session/bookkeeping/storeMaintenanceWriteSql.ts:44-55`; `src/__tests__/bookkeeping-cache-publication.test.ts:178-195`.

Required correction: Coordinate with P4/#1244: preserve immediate reset at the public clear entry point and approved Promise completion/best-effort policy; retain COMMIT hooks for ordinary publication/eviction effects. ## Publication, lifecycle and ownership assessment

The examined SQL publication design is generally conservative about authority. Mapping/history/pin projection, resource promotion, publication-lease release and route publication join one outer transaction. Nested false/throw/thenable becomes rollback-only; hooks are discarded. Occupied UUID and absent durable fence-slot generations prevent simple ABA after eviction/tombstone pruning. Rollback snapshots use canonical metadata while imported raw legacy history/CAS bytes remain preserved until mutation. Unknown COMMIT poisons/reopens and retains durable authority instead of replaying the callback. Cache hooks only run after known successful COMMIT; the server retains a turn/no-replay barrier for uncertain publication (`server.ts:1875-1891,1908-1912`). F3 is the specific independent reset-command exception to that otherwise appropriate publication policy.

Process-death observation stays outside SQL. Acquisition/reconcile reread exact generation/rowVersion and full lease or deletion-owner/executor fields before applying it; changed incarnation/token/version invalidates the observation. Exact and legacy NULL pins are reread inside claim/retirement transactions. Active SDK writers, publication leases, tombstones and permanent deleting claims are distinct. The implementation does not discover ownership by enumerating transcript roots and does not read/modify private SDK transcript formats. Physical deletion uses the shared supported SDK deleteSession child path only after durable executor attachment. Marker/stub tests check gate-before/after COMMIT, parent SIGKILL and unjoined executor survival; custom-deleter uncertainty intentionally leaves a permanent fence. Double deferred counts for timed-out custom work are inherited JSON behavior and explicitly differential-tested; not reported as a new SQL defect.

Unarmed TTL recovery (including publication leases) retains the existing JSON policy and turn-watchdog assumption, not a newly invented SQL process-death rule. Armed unrecoverable writers cannot be cleared merely by apparent executor death; boot authority is required. Nonpublication exact prepare can return an existing deleting locator as legacy JSON does, but acquisition/publication still refuse the deleting state. No new ownership grant was inferred from that harmless identity-return path.

POSIX child cleanup joins the owned ChildProcess handle and checks process-group emptiness; unreaped owned handles avoid stale-PID kill decisions. Windows skips POSIX group emptiness under the existing assumption that SDK deleteSession only performs direct filesystem work and does not spawn descendants. The code preserves the stronger boot-only recovery for unrecoverable writer leases. No real Windows/libsql/SDK run was performed here; that platform claim remains a gate, not established by macOS source inspection.

Reconcile does release/yield between its 128-row page transactions and performs a rescue pass before retirement to free pending headroom. It nevertheless completes both passes before the deletion-phase deadline starts. That is distinct from the reproduced F1 claim loop, which never releases between its pages. Store count-cap/prune helpers and startup/offline audits also contain full metadata scans; this review does not infer a latency bound for arbitrary imported ledgers from runtime defaults or paging elsewhere. No additional cap-pruning benchmark was authorized or run by this child.
